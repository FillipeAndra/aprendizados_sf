
## Níveis de acesso

### Categorias principais

#### Organização

- Politicas de acesso voltadas à entrada de usuários na sua organização, especificando o login e senha deles

#### Objetos

- Realiza o controle de acesso a objetos específicos pertencentes ao ambiente da empresa. É possível controlar o acesso de leitura, alteração e/o exclusão de um objeto. Esses itens podem ser editados via conjuntos de permissões e grupos de permissões.

	- EX: um entrevistador não pode excluir ou alterar um currículo de um entrevistado, mas pode ler 

- É pertinente perceber que os objetos tem campos para armazenar quem criou o registro, isso está presente no histórico de modificações do objeto

- Pode ter seus acessos controlados por conjunto de permissões (permition sets)

#### Campos

- pode editar o acesso de visualização e/ou edição de um campo ou parte presente em alguns objetos. É configurado em conjunto de permissões

#### Registros

- restringe o acesso a dados presentes no mesmo objeto, que não foram criados pelo usuário que está agindo. (Ex: um vendedor não consegue ver o lead de outro)

- uma boa prática neste cenário é por padrão definir um nível de acesso padrão mínimo e ir liberando os acessos de visualização e interação com os registros através de hierarquia de funções, regras de compartilhamento de grupo ou através de mudança de regra no usuário específico

- sharing settings é o ambiente dentro de setup que controla as regras de compartilhamento da organização, o que permite criar o padrão geral de nível de acesso

## Como criar um objeto

1) vá no setup e digite Object Manager no quick find e entre no campo

2) Selecione create  e selecione custom object se quiser fazer do zero ou custom object from spreadsheet para pegar um template (os próximos passos se voltarão ao caso do custom object)

3) Os campos obrigatórios são:

	- rótulo
	- rótulo no plural
	- nome do objeto
	- nome do item que será gravado no objeto
	- e o tipo de dado que será gravado

4) é possível editar também funcionalidades adicionais como:

	- permitir relatório
	- permitir atividades
	- armazenar o histórico do campo
	- permitir o objeto em grupos de chatter

5) tambpem a classificação do objeto que é possível editar

6) É possível editar se está no ambiente de produção ou no de desenvolvimento

7) após editar os itens desejado basta salvar e o objeto está criado 
## Tipos de permissões

### Conjunto de permissões

- São coleções de configurações e permissões alocadas em um bloco que ao atribuir ele a um usuários todas as permissões de campos, registros e objetos serão vinculadas a esse usuários

- Seria algo similar às opções permissões específicas de uma rotina do winthor

#### Como criar um conjunto de permissões

- 1) Clique em configuração

- 2) Clique em busca rápida (Quick find) e digite "Permission Sets" ou "Conjuntos de permissões" e selecione a opção new

- 3) Clique em novo e insira: 
	- O título
	- A descrição
	- Pode-se selecionar qual licença vai ser o filtro das permissões desse conjunto (EX: Só usuários com licença de Chatter podem receber esse conjunto de permissões) ou  pode escolher adicionar o conjunto futuramente para cada usuário e salve

- 4)  Para configurar as permissões de objeto do conjunto de permissões selecione a opção object settings e selecione um objeto

- 5) clique em editar e selecione as opções de objeto e campo desse objeto que deseja que estejam ativas. Ao fim, clique em salvar

- 6) click no link de permission set overview para voltar para a tela de conjunto de permissões

- 7) As permissões de usuário estão no submenu de APP permissions, onde para editar basta apenas selecionar as opções desejadas e salvar

### Conjunto de permissões baseada em seção

- É um permission set que se baseia no fato de enquanto um usuário estiver com a sessão ativa (logado) ele tem as permissões presentes naquela permission set, quando ele desloga ou caso haja alguma configuração de tempo limitado de sessão, ele é obrigado a confimar que ele está logado para poder continuar tendo as permissões

- EX caso hipotético: caso seja criada a limitação de uma sala de entrevistas que tem um access point com uma faixa de ip específica, assim, para caso os entrevistadores queiram ter a permission set de editar o registro do entrevistado, ele só vão ter acesso  quando estiverem na sala de de entrevista

- Ela é mais utilizada em aplicações que se comunicam com a api da Sales force para confirmar que uma sessão está ativa, servindo como uma verificação para liberação de permissão.

	-  Na soap API do salesforce o nome do campo para verificar se a permission set precisa de ativação da sessão é HasActivationRequired que retorna true ou false 

	- Se através da API você mandar o session id e a permission set (nome da permission set para API) para a rota de SessionPermSetActivation a permission set vai entender que a sessão está ativa

#### Criando um session-based permission set

1) acesse o saleforce como admin, depois entre em setup, em seguida pesquise por permission set no quick find

2) clique em new (novo)

3)  coloque o nome da label (rótulo) e o nome na api já vem automaticamente ao clicar no campo depois de escrever a label

4) selecione a **checkbox Session activation require** para ativar a limitação da sessão ativa

5) License none (caso queira que a permission set não esteja associado a uma licensa) e então salve e a partir desse ponto é só colocar as regras de objeto, aplicativo ou qualquer regra que deseje.
### Grupo de conjunto de permissões

- um grupo de conjunto de permissões é um aglomerado de conjunto de permissões usado para agrupar permissões voltados geralmente à um cargo ou função. 

 - Seria algo similar a um perfil padrão utilizado no Winthor onde já vem com os acessos configurados voltados para cada tipo de usuário

- cada grupo de conjunto de permissões pode ser alocado com quaisquer conjunto de permissões desejadas

- quando se deseja impedir a ação de uma permissão em um conjunto de permissões em um determinado grupo de conjunto de permissões, basta silenciar essa permissão

- É possível também importar permissions sets de um app que você instalou no ambiente (que já vem com essas permission sets) em um permission sets group do seu ambiente. Isso auxilia n processo de quando o app receber uma atualização e mudar as permissões de uma permission set você já vai estar atualizado de imediato, sem precisar tomar uma ação. 

- Para facilitar a analise das permissões de usuário é possível usar o app User access and permissions assistenat presente na loja appexchange da sales force

#### Criação do grupo de conjunto de permissões

- 1) entre em Setup (Configuração), clique em Quick find (Busca rápida) e pesquise por permission set groups (grupos de conjunto de permissões) e selecione o item

- 2) Clique em New permission set group (novo grupo de conjunto de permissões)

- 3) Coloque o nome do grupo e a descrição e salve

- 4) na página de visão geral do grupo clique em permission sets in group 

- 5) Nessa página clique em add permission set e selecione os conjuntos de permissões que quer adicionar. Ao conluir a seleção cliquem em Add e por fim em done.

#### Silenciar uma permissão em um grupo de conjunto de permissões

- você só pode silenciar até uma unidade de permission set, mas você pode sileneciar diversos objetos, campos, user permissions e outras configurações de acesso.   

- o que geralmente vai acontecer para precisar usar essa feature é quando um grupo precisar mais permissão que outro de uma permission set já existente 
	
	- e então primeiro é criado uma regra de mutting das futuras novas permissões, no grupo já existente 
	
	- e depois você dá as permissões que vão ser necessárias no permission set para o novo permission set group 
	
	- então agora você cria o novo permission set group para o novo uso e associa a quem precisa usar essas novas permissões

- quando se muta permissões de uma permission set que são prévias as outras, as suas dependentes também são mutadas. EX: se read for mutado, edit, delete e create também são mutadas por consequência

 1) Na pagina de visão geral do grupo de conjunto de permissões desejado clique em Muting permission set in group (Silenciando conjunto de permissões no grupo)

 2) Clique em new (novo) e escreva o nome desejado tanto na API quanto na label e salve

3) Clique no silenciamento criado e vá para objetos ou permissões através da caixa de Find settings ou vá por meio da seção que tem as permissões que se deseja silenciar

4) clique em edit e marque a caixa de seleção na coluna muted (silenciado) do que você deseja silenciar, seja ela a tab settings, object settings e/ou campos.

#### Atribuição de um grupo de conjunto de permissões

- 1) Na pagina de visão geral do grupo vá na aba de manage assignments (Gerenciar atribuições) e clique em add assignments

- 2) Selecione os usuários que receberam as permissões do grupo e clique em next

	- 2.5) Caso deseje dar essas permissões temporariamente atribua uma data de vencimento para o usuário

- 3) Clique em assing (atribuir).

## Atribuição de nível de acesso à um objeto

- No sales force o certo é criar um nível mínimo padrão com geralmente read only ou private e ir acrescentando acessos através da criação de grupos com mais acessos acrescidos ou usando papeis de hierarquia para manter o controle de acesso.

### Formas de gerenciar permissões de objetos

#### Conjunto de permissões (permission sets)

- aqui é definido as permissões de objeto, campo e usuário que cada usuário vai ter.

- É possível montar diversos conjuntos de permissões para cada cenário de tarefa específica, como realizar o processo de tratativa de lead de forma limitada para atender somente o que o vendedor precisa.

- um único usuário pode ter um várias liberações associadas para realizar permitir o acesso a todos os recursos que ele necessita

#### Permission set groups (grupos de conjunto de permissões)

- os grupos são a junção de vários conjuntos de permissões que seria um comparativo de um usuário padrão utilizado no winthor

- Um usuário pode ter vários grupos de permissões associados a ele, então a totalidade de suas permissões é o somatório das permissões presentes neles 

#### Perfis

- Usado para criar configurações padrão de um usuário, geralmente baseado em uma licença de aplicação como chatter

### Níveis de acesso

- Privado: somente o proprietário do registro e seus superiores podem ter acesso ao registro desse objeto, podendo ver, editar o registro e gerar um relatório.

- Somente leitura pública: Todos podem ver os registros, mas apenas o criador dos registros e seus superiores podem editar eles.

- Leitura e gravação pública: todos podem ler, editar e gerar relatório de todos os registros do objeto

- controlado pelo pai: um usuário tem acesso a um registro com esse tipo de controle caso este usuário já tenha acesso ao registro pai (registro do qual o registro desejado tenha origem). Neste cenário o usuário tem o mesmo tipo de acesso ao registro filho que ele tem no caso do registro pai.

### Perfis padrão 

- Os perfis padrão já vem inclusos na Salesforce e vem associados a uma licença de aplicação, as permissões nesses casos já vem definidas relacionado aos perfis

- Os perfis padrões não podem ter suas permissões de objeto editadas diretamente, entretanto é possível realizar clonagem dos perfis padrões e modificar o perfil clonado

- O recomendado é conceder ou o munimum access - salesforce ou um clone dele com permissões reduzidas aos colaboradores e ir adicionando permissões com 

#### Criar e atribuir um perfil

##### Criação

1) Entre em Setup e na barra de quick find digite profiles (perfis) 

2) Na tela de perfis selecione a opção "clone" ao lado do perfil que deseja que seja clonado

3) Digite o nome do novo perfil e salve

4) Defina os níveis de acessos à objetos do novo perfil e salve

##### Atribuição

1) Em setup digite Users no quick find entre na opção

2) Selecione a conta que deseja alterar o perfil

3) clique em edit

4) Selecione o perfil que seja fixar no usuário no campo Profile e salve

### Acesso à campos 

- Ao alterar a visibilidade de um campo para um permission set e/ou premission set groups de um usuário ele deixa de aparecer não somente para o objeto a qual ele faz parte, mas também qualquer relatório, pesquisa ou outro processo em que poderia aparecer

- O nível de acesso pode ser editado, de dentro de um perfil (mudança fica associada somente ao perfil), de dentro de um permission set (mudança fica associada ao permission set) ou no menu de Field Accessibility (configuração vai para toda a organização)

- Tem alguns campos que as permissões já vem fixas por padrão, impossibilitando sua edição

- após mudar o acesso de um campo, é possível cria um layout da página onde o campo aparece (ou não) para o usuário e como fica o layout de pesquisa, com ou sem o campo

- O field accessibility também serve para verificar quais usuários/perfis tem acesso ao campo

#### configuração de acesso aos campos para um permission set

1) Acesse como admin, entre em Setup, pesquise por Permission Sets

2) entre em uma permissão para editar um objeto ou crie uma nova permission set (seguiremos com o caminho da criação de uma permission set)

3) Nomeie a permition set e para a associação à uma licença específica é recomendado que selecione None. Após isso salve.

4) Entre na permission set desejada, acesse o object settings e entre no objeto desejado

5) Vá para a sessão de field permission dentro do objeto e edite as premissões dos campos entre não possível de visualizar (e não possível de editar), possível apenas de visualizar (read) e possível de visualizar e de editar (edit) e depois salve suas modificações.

#### Como criar um campo (Field)

1) Entre como admin, vá para setup e no quick find pesquise por Object Manager e selecione a opção

2) No quick find de dentro dessa tela selecione o objeto que você deseja editar e clique no nome dele

3) Na aba lateral esquerda selecione a opção Fields & Relationship

4) Selecione a opção New 

5) Selecione a tipagem do campo (sim, é como se você estivesse criando uma coluna de uma tabela em um banco) e depois clique em next

6) dê um nome para a label e o nome do campo. Caso precise selecione ou desmarque as opções adicionais presentes nessa tela derivado da seleção  do tipo do campo. Quando concluir essa etapa clique em next

7) Selecione quem terá visibilidade do campo para cada Profile e se quem tem visibilidade apenas para ver (recomenda-se apenas marcar a checkbox visible para o system administrator, ara as pessoas só verem o campo através da liberação de um permission set). Quando finalizar, clique em next

8) Deixe a checkbox Add Field para o objeto desejado marcada e aparte em save para salvar a modificação e sair da tela de criação de um campo ou aperte em save & new para continuar a criar mais campos.

#### Mudar os acessos de um campo para múltiplos permission sets

1) Como admin entre em setup e no quick find pesquise por User Management settings

2) Dentro desse Menu libere a permissão Field-Level Security for Permission Sets during Field Creation (segurança de nível do campo para configurações de permissão durante a criação do campo)

3) Vá para o quick find principal e procure por Object Manager

4) Dentro do quick find desse menu pesquise pelo nome do bojeto que deseja editar os campos e clique no nome dele quando encontrar

5) Na aba lateral selecione Fields & Relationship

6) no quick find desse sub-menu digite o nome do campo que deseja editar e depois clique no nome dele

7) Clique no botão Set field level security

8) observe pelo nome das permission sets presentes aqui e selecione se ela(s) deve(m) ter acesso de leitura e/ou edição

9) Ao finalizar salve a modificação 

### Acesso à registros

- Para controlar os registro que devem pertencer a um usuário ou que ele deve ter acesso é através de permission sets, permission sets groups e através de seus perfis

-  Para controlar o acesso à registros que um usuário não detem é preciso realizar 4 controles de acesso. Segue eles do que deve ser mais restritivo para o menos:

1) **Sharing settings** (Controle de acesso da organização (organization-wide defaults)): Serve neste cenário para configurar que os usuários normalmente não devem acessar registros que não foram criados por eles.

2) Hierarquia de papeis (**roles**) (role hierarchies): serve para garantir que os gerentes tem acesso aos mesmos registros que os seus subordinados (EX: o gerente do comercial te acesso a todos os registros de cada um dos membros de seu time)

3) Configurações de compartilhamento (**Sharing rules**): são regras que garantem que certos grupos de usuários tenham acessos que não seriam permitidos normalmente pelo organization-wide defaults

4) **Manual sharing**: serve para permitir que certos usuários compartilhem certos arquivos (que sejam seus ou, dependendo da configuração, que tenham apenas acesso)  com outros usuários que passam a ter acesso aos registros

#### Organization-wide defaults (org-wide defaults)

- tem que ser o mais restritivo possível

- se baseia no princípio de pensar no cenário de pessoa com maior restrição da empresa e este cenário se torna a regra, para assim só ir liberando acesso via hierarquia, regras de compartilhamento e compartilhamento manual

- a configurarção ocorre separadamente para cada objeto, limitando se a pessoa vê ou não e caso ela veja se ela é capaz de editar para os tipos de usuários (interno ou externo)

##### Definição dos padrões de compartilhamento para toda organização (org-wide sharing settings)

1) Vá para configuração pesquise sharing settings (configurações de compartilhamento) no quick find (busca rápida)

 2) clique em edit (editar) na área organization-wide defaults (padrões para toda a organização)

 3) Pra cada objeto, selecione a opção de acesso padrão desejado na coluna Default Internal Access (acesso interno padrão) para acesso interno ou mude a configuração de compartilhamento do objeto na default external access para mudar o compartilhamento externo.

 4) Para permitir que usuários com níveis hierárquicos superiores tem mais acessos para este objeto de forma automática, selecione a opção grant access using hierarchies (conceder acesso usando hierarquias) no objeto desejado caso, ele não esteja como controlled by parent. Por fim salve.

5) Ao salvar espere o recebimento do e-mail confirmando que a refatoração dos acessos terminou (demora um pouco).

#### Criação de uma hierarquia de papeis (role)

- Ao criar hierarquia ela controla o nível de acesso à dados permitindo que os cargos acima tenha acesso aos registros que os papeis diretamente abaixo também tenham ou os registros que foram compartilhados com estes. 

- O nome não necessariamente precisa bater com um nome de cargo real, a hierarquia no Salesforce é apenas um controle de níveis de acesso

##### Criação de hierarquia e edição

1) Acesse como admin, entre em setup e pesquise por rules no quick find

2) se estiver aparecendo a tela de understanding rules (entendo os papeis) selecione o botão Set up rules (caso não, ignore)

3) quando a hierarquia abre ela começa pela organização, que se expande para a posição mais alta na hierarquia. A edição ou acrescento de um item da hierarquia sempre vai se direcionando para baixo. 

4) ao lado de um papel fica as opções edit para editar o papel, del para excluir e assing para alocar um usuário a aquele papel

5) Em baixo de cada papel (quando está na visualização em árvore) fica o botão de add role para adicionar um papel subordinado a ele

6) Ao **Criar um papel** é necessário colocar um label (rótulo), role name (nome do papel), e this role reports to (esse papel reporta à) para indicar de quem ele é subordinado e depois aperta save para salvar.

#### Criação de regras de compartilhamento 

- Para a criação de regras de compartilhamento há 3 pontos principais de análise:
	
	- Quais os registros a serem compartilhados, com quem serão compartilhados e qual o tipo de acesso vai ser dado para quem recebeu o compartilhamento (apenas leitura ou leitura e edição).

	- o critério de **Quais registros serão compartilhados** pode se basear em quem detêm os registros ou os registros específicos que atendam a um critério escolhido

	- os critérios de **Com qual usuário compartilhado** podem ser por papeis,  por território ou pela criação de um grupo público

		- Território: uma organização que pode ser criada baseada em uma separação regional (a exemplo de filiais). geralmente são utilizados para garantir no mínimo a capacidade de leitura dos registros entre todos os membros e cada território tem sua própria hierarquia.
		
		- Public group: um grupo de membros são agrupados pelo admin para replicar regras de compartilhamento. 
			
			- Geralmente os grupos públicos podem ser uma combinação de contas individuais, papeis, papeis e subordinados, territórios, territórios e subordinados, e outros grupos públicos. 
			- Geralmente o critério recomendado é a aglomeração de usuários que tem a mesma função dentro de um contexto, por exemplo, todos os desenvolvedores tem acesso de leitura à todo o acervo de código da empresa.

- Antes da criação de uma sharing rule, tem que ser avaliado se o nível de complexidade do filtro necessário para funcionar é tão grande para apenas um conjunto pequenos de pessoas que valeria mais apena fazer o compartilhamento manual entre eles

##### Criando grupo público

1) primeiro acesso como admin, vá para setup, e no quick find digite public groups e entre na opção

2) Clique em new e adicione um rótulo do grupo (o nome é preenchido automaticamente)

3) adicione os membros que deseja filtrando pelo campo de search e for e vá adicionando ou removendo os membras da área de selected members

4) por fim salve o que foi feito.

5) caso precise editar os usuários de um grupo público basta fazer o passo 1, depois clicar no nome do grupo que deseja editar > clicar em editar > fazer os passos 3 e 4.


##### Definindo regras de compartilhamento (sharing rules)

1) entre como admin, vá para o menu de setup e pesquise por sharing settins 

2) no filtro manage sharing settings for, selecione o objeto presente na lista ao qual deseje criar uma regra

3) vá para a área de sharing rules presente na página e clique em novo (new)

4) para o tipo de regra (select your rule type) há duas possibilidades, a de ser uma regra com o filtro do usuário que detêm o registro original ou uma regra baseada em critérios pertencentes ao registro daquele objeto (seguiremos com o de usuário criador)

	1) quando for por critério do registro, é necessário que você selecione um campo (Field) e faça uma operação de verificação para caso essa verificação seja verdadeira, o compartilhamento ocorra.

5) O campo de select witch records to be shared você seleciona quais grupos, papeis ou papeis e seus subordinados que são os donos do registro que deseja que seja compartilhado

6) No campo select the users to share with é para selecionar com quais grupos, papeis ou papeis e seus subordinados com o qual o registro vai ser compartilhado.

7) por fim selecione o nível de acesso que as pessoas que vão receber o registro vão ter: apenas leitura ou leitura e escrita. Ao finalizar salve as modificações com o botão save.

8) Por fim aguar o e-mail avisando que a recalibração terminou


#### Account Teams (times de contas)

- Quando essa feature é liberada permite aos usuários com autorização criar pequenos grupos com outros usuários para compartilhar registros para facilitar a realização de um trabalho

1) Acesse o Salesforce como admin, entre em setup e no quick find pesquise por account team

2) dentro dessa configuração permita a criação de account teams selecionando o enable e salve

3) selecione o account layouts (essa funcionalidade passa a fazer parte de accounts) e o add to users customizaed realated list (adiciona os times na lista de contas relacionadas que os usuários podem criar) e salve.

4) é possível adicionar mais papeis para times clicando em team roles e depois em new. Basta escrever em linhas separadas cada função que deseja adicionar, depois só precisa salvar

5) cara criar um time padrão para associar a algum projeto seu, basta ir nas definições avançadas do seu usuário e depois criar o seu time adicionando os membros (incluindo você mesmo) e  configurando o que cada um vai ter acesso, depois basta salvar.
